# [AI TOOL] AI 코딩 툴별 프롬프트 정리 — v0 / Replit / Bolt.new / Lovable

> 여행 자금 관리 서비스 UI 목업을 만들면서 툴별로 작성했던 프롬프트와, 왜 그렇게 구성했는지,
> 각 툴에서 특히 주의해야 할 점을 정리한 문서.

---

## 0. 공통 설계 원칙

툴마다 프롬프트를 조금씩 다르게 썼지만, 아래 원칙은 4개 모두에 공통으로 깔려 있다.

- **화면을 경로(route) 단위로 명시** — "지출 입력 화면"이 아니라 `/rooms/[roomId]/expenses/new`처럼 실제 URL로 지정하면 AI가 라우팅 구조를 스스로 정확히 잡는다.
- **구성 요소를 개수·순서까지 리스트로 명시** — "카드 3~4개", "2컬럼/1컬럼"처럼 숫자로 못 박으면 결과물 편차가 줄어든다.
- **화면별 설명에 "이동 흐름"을 포함** — "등록 시 어디로 이동"까지 적어야 버튼이 실제로 동작하는 UI가 나온다.
- **mock 데이터 처리 방식을 별도로 지시** — "배열/객체로 상단에 선언"이라고 못 박아야 나중에 실제 API로 교체하기 쉬운 구조가 나온다.
- **공통 요구사항(반응형, 톤)과 화면별 요구사항을 분리** — 톤 얘기를 화면마다 반복하면 오히려 화면마다 미묘하게 다른 스타일이 나올 위험이 있다.

## 1. v0

### 작성했던 프롬프트

```
Next.js + Tailwind + shadcn/ui로 여행 자금 관리 서비스의 "방 대시보드" 화면을 만들어줘.

[맥락]
여러 명이 함께 여행 자금을 모으고, 지출을 기록하고, 나중에 정산하는 협업 서비스의 메인 화면이야.
지금은 UI 목업 단계라 실제 API 연동 없이 mock 데이터로 구성해줘.

[레이아웃]
- 상단: 여행 제목("도쿄 여행"), D-day 뱃지, 참여 멤버 아바타 목록
- 목표 금액 대비 적립 진행률 프로그레스 바 (예: 목표 3,000,000원 중 1,800,000원 적립, 60%)
- 멤버별 적립 현황 카드 4개 (이름, 아바타, 개인 목표 대비 적립액)
- 최근 지출 내역 리스트 3~5건 (장소/항목, 금액, 결제자 아바타, 날짜) — 카드 형태
- 우측 상단 또는 플로팅 형태로 "지출 등록" 버튼 (눈에 띄게)
- 반응형: 데스크톱은 2컬럼(적립 현황 + 지출 내역 나란히), 모바일은 1컬럼 스택

[톤]
깔끔하고 신뢰감 있는 톤, 파란색 계열 포인트 컬러, 카드 기반 구성, 과한 장식 없이.

mock 데이터는 컴포넌트 상단에 배열로 정의해서 나중에 실제 데이터로 바꾸기 쉽게 해줘.
```

화면을 이어갈 때 쓴 후속 프롬프트:
- `"같은 스타일로 지출 입력 모달 화면도 만들어줘. 장소/항목명, 금액, 결제자 선택(아바타), 정산 대상 멤버 다중 선택(기본 전체 선택) 필드 포함해줘"`
- `"같은 스타일로 정산 결과 화면 만들어줘. 멤버별 낸 금액/부담액/차액 테이블이랑, 'A → B에게 32,000원' 형태의 송금 안내 리스트 포함해줘"`

### 왜 이렇게 작성했나

- v0는 **한 화면씩 요청할 때 결과 품질이 가장 좋은 툴**이라, 전체 사이트맵을 한 번에 넣지 않고 "방 대시보드" 하나만 먼저 상세히 요청했다.
- shadcn/ui, Tailwind처럼 v0가 기본으로 채택하는 라이브러리명을 그대로 명시해서, v0의 기본 컨벤션과 충돌하지 않게 했다.
- 이후 화면은 `"같은 스타일로"`라는 표현으로 이전 대화 맥락(색상, 레이아웃 톤)을 이어받게 했다 — v0는 같은 세션 안에서는 이전 화면의 스타일을 잘 기억하는 편이라 매번 톤을 재설명할 필요가 없었다.

### 주의할 점 / 고려할 점

- **화면 단위 생성이라 화면 간 톤이 미묘하게 어긋날 수 있다.** 특히 세션을 나눠서 요청하거나, 시간 간격을 두고 이어가면 색상 톤(파란색의 채도 등)이 조금씩 달라지는 경우가 있어 마지막에 전체 화면을 나란히 띄워 톤 통일 여부를 확인해야 한다.
- **로그인, API 연동, 상태관리(Zustand/TanStack Query)는 거의 만들어주지 않는다.** v0는 "UI 생성기"에 가까워서, 인터랙션 로직이 필요한 부분은 이후 Cursor 등에서 직접 붙여야 한다.
- 결과물이 v0 플랫폼(샌드박스) 안에 있으므로, **코드를 프로젝트로 복사해오는 작업이 화면마다 별도로 필요**하다. 화면이 많아질수록 이 작업의 누적 비용이 커진다.

## 2. Replit

### 작성했던 프롬프트

```
Next.js(App Router) + TypeScript + Tailwind CSS로 "여행 자금 관리" 서비스의
UI 목업 프로젝트를 만들어줘. 지금은 백엔드/DB 연동 없이 mock 데이터 기반의
정적 화면 프로토타입 단계야.

[페이지 구성]
- /login : 로그인/회원가입 화면
- /rooms : 내 방 목록 (참여 중인 방 카드 리스트, 새 방 만들기 버튼)
- /rooms/new : 방 생성 폼 (여행 제목, 시작일/종료일, 목표 금액, 인원수 입력, 1인당 월 적립 예상액 미리보기)
- /rooms/[roomId] : 방 대시보드 (D-day, 적립 진행률, 멤버별 적립 현황, 최근 지출 미리보기)
- /rooms/[roomId]/expenses : 지출 목록 (필터, 총 지출액 요약)
- /rooms/[roomId]/expenses/new : 지출 입력 폼 (장소/항목, 금액, 결제자, 정산 대상 멤버 다중선택)
- /rooms/[roomId]/settlement : 정산 결과 (멤버별 낸 금액/부담액/차액, 송금 안내 리스트)
- /invite/[token] : 초대 링크 접속 화면

[공통 요구사항]
- 페이지 간 이동은 실제 라우팅으로 동작하게 해줘 (Next.js Link 사용)
- 모든 데이터는 각 페이지 상단에 mock 배열/객체로 선언
- 공통 레이아웃(상단 네비게이션, 방 이름 표시)을 shared layout으로 분리
- 반응형 디자인 (모바일 1컬럼, 데스크톱 2컬럼 위주)
- 깔끔한 카드 기반 UI, 파란색 계열 포인트 컬러

이 단계에서는 폼 제출이나 API 호출 로직은 필요 없고,
클릭했을 때 페이지 이동만 잘 되는 수준의 목업이면 돼.
```

### 왜 이렇게 작성했나

- Replit Agent는 **에이전트가 프로젝트 전체를 한 번에 스캐폴딩하는 방식**이라, v0처럼 화면 하나씩 나누지 않고 전체 페이지 목록을 한 번에 줬다.
- "실제 라우팅으로 동작"을 강조한 이유는, Replit Agent가 종종 페이지를 만들어놓고도 서로 링크를 안 걸어두는 경우가 있어서 미리 못 박아둔 것이다.
- 공통 레이아웃을 "shared layout으로 분리"라고 명시한 것은, 에이전트가 페이지마다 네비게이션 바를 중복 작성하는 것을 막기 위함이다.

### 주의할 점 / 고려할 점

- Replit Agent는 **작업 범위가 크면 중간에 엉뚱한 방향으로 새는(=wander) 경우가 있다.** 페이지 8개를 한 번에 요청했을 때 일부 페이지가 부실하게 나올 수 있어, 완료 후 페이지별로 빠짐없이 확인하는 과정이 필요하다.
- Git이 기본 워크플로우가 아니라서, **GitHub으로 옮기려면 별도로 git remote 연결이나 zip 다운로드 후 로컬 이전 작업**이 필요하다.
- React/Next.js 전용 툴이 아니라 범용 에이전트라서, 프론트엔드 관례(App Router 컨벤션 등)를 다른 툴보다 덜 엄격하게 지킬 수 있다 — 결과물의 폴더 구조를 반드시 확인해야 한다.

## 3. Bolt.new

### 작성했던 프롬프트 (최종 버전 — 방 설정/초대 기능 포함)

```
Next.js(App Router) + TypeScript + Tailwind CSS로 "여행 자금 관리" 서비스의
UI 목업 프로토타입을 만들어줘. 지금은 백엔드/DB 연동 없이 mock 데이터 기반의
정적 화면 단계이고, 페이지 간 이동은 실제 라우팅으로 동작해야 해.

[서비스 개요]
여행을 준비하는 사람들이 방(Room)을 만들고, 초대된 멤버들과 함께
① 여행 전 자금 모으기 ② 여행 중 지출 기록 ③ 여행 후 정산까지 처리하는 협업형 웹 서비스.

[페이지 구성 및 각 화면 상세]

1. /login — 로그인/회원가입
- 이메일 로그인 폼, 소셜 로그인 버튼
- 회원가입 폼(이름, 이메일, 비밀번호)

2. /rooms — 내 방 목록
- 참여 중인 방 카드 리스트 (방 이름, 여행 일정, D-day, 진행 상태 뱃지)
- "새 방 만들기" 버튼 → /rooms/new 로 이동

3. /rooms/new — 방 생성
- 여행 제목, 시작일/종료일 입력
- "모으기 기능 사용" 토글 스위치 — 켜져 있을 때만 목표 금액, 예상 인원 입력 필드가 나타남
- 모으기 켜진 상태에서 목표 금액/인원 입력 시 실시간으로 "1인당 월 적립 예상액" 미리보기 표시
- 생성 완료 버튼 → 생성 직후 바로 초대 화면(4번)으로 자연스럽게 이어지도록 구성

4. /invite/[token] — 초대 링크 접속/공유
- (a) 방장이 대시보드에서 "멤버 초대" 버튼을 눌러 들어온 경우 → 초대 코드/링크와 공유 버튼이 크게 보임
- (b) 초대받은 사람이 링크로 직접 들어온 경우 → 방 이름/여행 일정 요약 + "참여하기" 버튼
- 현재 참여 중인 멤버 아바타 리스트(방장 표시 포함)

5. /rooms/[roomId] — 방 대시보드 (메인 화면)
- 상단: 여행 제목, D-day 뱃지, 참여 멤버 아바타들 + "멤버 초대" 버튼("+" 형태)
- 모으기 기능이 켜진 방이면 목표 금액 대비 적립 진행률 프로그레스 바
- 모으기 기능이 꺼진 방이면 "지출 기록/정산만 사용 중" 안내 문구로 대체
- 멤버별 적립 현황 카드 3~4개(모으기 켜진 경우만)
- 최근 지출 내역 미리보기 3~5건
- "지출 등록" 버튼 → /rooms/[roomId]/expenses/new 로 이동
- 데스크톱 2컬럼, 모바일 1컬럼

6. /rooms/[roomId]/expenses — 지출 목록
- 날짜순 리스트, 멤버별/카테고리 필터, 총 지출액 요약

7. /rooms/[roomId]/expenses/new — 지출 입력 폼
- 장소/항목명, 금액, 결제자(단일 선택), 정산 대상 멤버(다중 선택, 기본 전체), 날짜(선택)
- 등록 시 /rooms/[roomId]/expenses 로 이동

8. /rooms/[roomId]/settlement — 정산 결과
- 멤버별 "낸 금액/부담액/차액" 요약, 송금 안내 리스트("A → B에게 32,000원")
- "정산 완료 처리" 버튼(mock)

9. /rooms/[roomId]/settings — 방 설정 (방장 전용)
- 여행 제목/일정/목표 금액 수정, 멤버 강퇴, 초대 코드 재발급, "멤버 초대" 바로가기

[공통 요구사항]
- 공통 레이아웃: 상단 네비게이션 바, 방 내 서브 메뉴(대시보드/지출/정산/설정)
- 모든 mock 데이터는 배열/객체로 선언
- 실제 API 호출 로직 없이 클릭 시 화면 이동 및 상태 변화(프로그레스 바, 토글 등)만 자연스럽게 동작
- 반응형 디자인

[디자인 톤]
파란색 계열 포인트 컬러, 카드 기반 레이아웃, lucide-react 아이콘, 시스템 기본 sans-serif.
```

### 왜 이렇게 작성했나

- Bolt.new는 **풀스택 전체를 한 번에 스캐폴딩**하는 툴이라, v0처럼 화면을 나누기보다 Replit처럼 전체 페이지 목록을 한 번에 상세히 줬다. 다만 Replit보다 화면별 세부 항목(구성 요소, 조건부 렌더링)을 더 촘촘히 적었는데, 이는 Bolt가 파일 트리를 실제로 보여주는 만큼 세부 지시가 그대로 파일 구조에 반영되는 경향이 있었기 때문이다.
- "모으기 기능 사용" 토글처럼 **조건부 UI 요구사항**을 명시한 이유는, 방 생성 폼을 짧게 유지하면서도 실제 기획(목표 금액이 필수가 아닌 경우)을 반영하기 위함이었다.
- 초대 화면을 "두 가지 진입 경로"로 나눠 설명한 것은, 방장이 대시보드에서 언제든 재진입할 수 있는 흐름과 초대받은 사람이 링크로 들어오는 흐름이 같은 화면을 공유하되 분기해야 한다는 점을 명확히 하기 위함이었다.

### 주의할 점 / 고려할 점

- Bolt.new는 **브라우저 안의 가상 환경(WebContainer)에서 돌아가기 때문에, 실제 컴퓨터와 100% 동일한 환경이 아니다.** 어떤 npm 라이브러리는 OS 레벨 기능이 필요해 WebContainer에서 지원되지 않을 수 있으므로, 나중에 상태관리(Zustand)나 폼 라이브러리(react-hook-form) 등을 추가할 때 의존성 충돌 여부를 확인해야 한다.
- 페이지 수가 많아질수록(9개) **한 번에 다 요청하면 일부 화면의 완성도가 떨어질 수 있다.** 전체 스캐폴딩 이후 화면별로 "이 화면만 더 다듬어줘" 식으로 후속 요청하는 것이 결과가 더 안정적이었다.
- 다행히 **GitHub push가 한 번의 클릭으로 가능**해서, 4개 툴 중 로컬 프로젝트로 이전하는 마찰이 가장 적은 편이다.

## 4. Lovable

### 작성했던 프롬프트

```
"여행 자금 관리" 서비스의 UI 프로토타입을 만들어줘.

[제품 설명]
여행을 준비하는 사람들이 방(Room)을 만들고, 초대된 멤버들과 함께
① 여행 전 자금 모으기 ② 여행 중 지출 기록 ③ 여행 후 정산까지 처리하는 협업형 웹 서비스야.

[중요] 지금 단계에서는 백엔드/데이터베이스 연동 없이, mock 데이터 기반의
정적 UI 프로토타입만 필요해. Supabase나 다른 백엔드는 아직 연결하지 마.
페이지 간 이동만 실제 라우팅으로 동작하면 돼.

[페이지 구성 및 각 화면 상세]
(v0/Bolt와 동일한 8개 화면 구성 — 로그인, 방 목록, 방 생성, 초대,
 대시보드, 지출 목록, 지출 입력, 정산 결과)

[공통 요구사항]
- 공통 레이아웃, mock 데이터 배열/객체 구성, 반응형 디자인

[디자인 톤]
깔끔하고 신뢰감 있는 톤, 파란색 계열 포인트 컬러, 카드 기반 레이아웃, lucide 아이콘.
```

### 왜 이렇게 작성했나

- Lovable은 **처음부터 Supabase 같은 백엔드 연동을 적극적으로 제안하는 성향**이 있어서, 다른 3개 툴과 달리 "[중요]" 태그를 따로 붙여 "백엔드는 아직 연결하지 마"라는 제약을 프롬프트 맨 앞부분에 강조했다. 이 문장이 없으면 첫 응답부터 인증/DB 연동 제안이 끼어들어 목업 단계에서 불필요한 복잡도가 생긴다.
- 나머지 화면 구성은 bolt.new용과 동일한 골자를 사용했는데, Lovable도 결국 "전체를 한 번에 만드는" 성격의 툴이라 상세한 페이지 리스트 방식이 잘 맞았기 때문이다.
- "Knowledge(프로젝트 지식)" 탭에 프로젝트 개요를 등록해두는 방식도 함께 활용했는데, 이는 프롬프트 자체는 아니지만 이후 화면을 이어서 요청할 때 매번 서비스 설명을 반복하지 않기 위한 보완 장치였다.

### 주의할 점 / 고려할 점

- **프로젝트가 Lovable 플랫폼 안에서 먼저 생성되고, 이후 GitHub과 동기화(sync)되는 구조**다. Cursor나 Bolt처럼 "내 repo가 먼저 있고 툴이 거기에 붙는" 방향이 아니라 반대 방향이라서, 실제 회사 프로젝트라면 이 순서 자체가 리뷰/CI 워크플로우와 충돌할 수 있다. 개인 프로젝트에서는 GitHub Sync 기능으로 연결하면 되지만, 연결 이후 폴더 구조를 우리 컨벤션에 맞게 다시 정리하는 과정이 필요할 수 있다.
- 크레딧 기반 과금이라, **화면을 이어서 다듬는 반복 작업이 많아지면 크레딧 소모가 빠르다.** 한 번에 요청할 내용을 최대한 명확히 정리해서 넣는 것이 비용 면에서도 유리하다.
- 스택 관련 "고집"이 다른 툴보다 강한 편이라, 이미 정해둔 스택(TanStack Query, Zustand, Zod)을 그대로 쓰고 싶다면 프롬프트에 명시적으로 못 박아야 한다. 명시하지 않으면 Lovable이 익숙한 자체 컨벤션(주로 Supabase + 자체 상태관리 패턴)으로 유도하는 경우가 있다.

## 5. 프로젝트에 이어서 요청할 때 공통으로 썼던 프롬프트 형식

4개 툴 모두, 초기 스캐폴딩 이후에는 아래처럼 짧게 요청하는 방식으로 전환했다.

```
지금 만들고 있는 "여행 자금 관리" 서비스 프로젝트에 이어서 작업할게.

[추가할 기능]
(예: 방 대시보드에 "멤버 초대" 버튼 추가)
- 위치, 클릭 시 동작을 구체적으로 서술

[제약사항]
- 지금까지 만든 다른 화면들과 톤 통일
- 아직 mock 데이터 단계니까 실제 API 연동이나 저장 로직은 넣지 말 것
```

스택/전체 구조 같은 초기 제약은 **프로젝트 시작 시 1번만 명확히 박아두고, 이후에는 "이번엔 뭘 추가/수정할지"와 "기존 제약을 벗어나지 말라는 확인" 두 가지만 짧게 얹는 방식**이 4개 툴 모두에서 효율적이었다. 다만 Lovable처럼 대화가 길어지면 초기 제약(백엔드 미연동 등)을 놓치는 경우가 있어, 그럴 때만 해당 제약을 다시 짚어주는 식으로 대응했다.

## 7. 실제 구현은 왜 Bolt.new로 확정했는가

4개 툴을 다 프롬프트로 만들어봤고, 이후 Bolt.new와 Lovable 두 곳은 실제로 GitHub push → clone → `npm run dev`까지 진행해 직접 비교했다. 최종적으로 Bolt.new를 메인 프로젝트로 확정한 이유는 다음과 같다.

- **Replit Agent는 확인된 이유로 제외** — React/Next.js 전용 툴이 아니라 App Router 컨벤션을 엄격히 따르지 않을 가능성이 높고, 실무에서도 프론트엔드보다 백엔드 실험/교육용으로 강점이 있다고 판단해 실제 구현 대상에서 제외했다.
- **v0는 확인된 이유로 제외** — 화면 단위 컴포넌트 생성기라 결과물을 프로젝트에 붙이려면 shadcn 세팅부터 화면별 코드 이식까지 수작업이 많이 필요하다. "탄탄한 시작점"보다는 "화면 초안 보조 도구"에 가깝다고 판단했다.
- **Bolt.new와 Lovable 비교에서 결정적이었던 것은 프레임워크 자체의 불일치였다** — 동일하게 "Next.js(App Router)로 만들어달라"고 프롬프트에 명시했음에도, 실제로 프로젝트를 clone해서 `npm run dev`로 실행해보니 **Bolt.new는 Next.js로, Lovable은 Vite + React로 결과물이 나왔다.** Lovable은 자체 기본 스택(Vite/React/Supabase)을 강하게 유지하는 경향이 있어 프롬프트의 프레임워크 지정이 지켜지지 않았다.
- **Next.js를 선택한 이유** — 실제 서비스로 배포할 경우 검색 엔진 노출(SEO)을 고려해야 하는데, Vite 기반 SPA보다 Next.js의 SSR/SSG가 이 부분에 유리하다고 판단했다. 방 대시보드처럼 로그인 이후의 개인화된 화면 자체는 SEO와 무관하지만, 서비스 랜딩 페이지 등 검색 노출이 필요한 부분과 SSR 경험을 포트폴리오에 남기고 싶다는 이유도 있었다.
- 결과적으로 Lovable(Vite)과 Bolt.new(Next.js)는 같은 프롬프트로도 완전히 다른 프레임워크로 귀결되었고, 이후 개발 로드맵(App Router 라우팅, Server Action/API Route 구분 등)이 전부 Next.js를 전제로 짜여 있었기 때문에 Bolt.new가 자연스럽게 메인 프로젝트로 확정되었다.

## 추가 — 미감(디자인 완성도) 관점에서의 개인적인 순위

실제 구현으로 이어갈 수 있는지와는 별개로, 순수하게 결과물의 디자인 완성도만 놓고 보면 아래 순서로 만족스러웠다.

> **Lovable > Bolt.new > Replit Agent > v0**

프롬프트에서 색상 톤, 레이아웃, 컴포넌트 구성 등을 최대한 구체적으로 제한해두었음에도, Lovable과 Bolt.new가 그 제약 안에서 더 완성도 있는 결과물을 보여줬다.

반면 v0는 화면 하나당 프롬프트 하나씩 독립적으로 생성해나가는 구조라, 개별 화면의 완성도는 나쁘지 않았지만 **전체 서비스의 목업을 한 번에 훑어보고 싶은 상황에는 맞지 않았다.** 화면을 이어서 요청할 때마다 이전 톤을 기억해주긴 했지만, 결국 화면 수가 늘어날수록 전체를 한눈에 확인하기 어려운 구조라는 한계가 있었다.
